# Kocom RS485 프로토콜 (Thermo 범위)

참조 구현(`clipman/kocom.py`)의 동작에서 정리한 사실. 코드는 옮기지 않는다 (ADR-0011).
**[검증 필요]** 표시는 실기기 캡처(`docs/capture-guide.md`)로 확인해야 하는 항목.

## 물리 계층

- RS485, 9600 bps, 8N1. EW11이 TCP 서버로 노출 (기본 포트 8899).

## Packet (21바이트)

| 인덱스 | 길이 | 필드 | 값 |
|---|---|---|---|
| 0–1 | 2 | 헤더 | `aa 55` |
| 2–3 | 2 | 타입(상위 12비트) + seq(하위 4비트) | 타입 `30b`=send, `30d`=ack / seq `c`,`d`,`e`,`f` = 1~4번째 시도 |
| 4 | 1 | monitor | `00` (월패드) |
| 5–6 | 2 | 목적지 주소 | 장치 코드 + 서브 ID |
| 7–8 | 2 | 출발지 주소 | 장치 코드 + 서브 ID |
| 9 | 1 | 명령 | `00` state, `3a` query (`01` on, `02` off — Thermo에서는 미사용) |
| 10–17 | 8 | 값 | 장치별 |
| 18 | 1 | 체크섬 | 인덱스 2~17 바이트 합 mod 256 |
| 19–20 | 2 | 트레일러 | `0d 0d` |

예: `aa55 30bc 00 0044 0001 00 0300000000000000 35 0d0d` (원본 주석에 있던 실제 패킷, 체크섬 일치 확인됨)

## 주소

- 장치 코드: `01` Wallpad, `36` Thermo
- Thermo 서브 ID = Room: `00` livingroom, `01` bedroom, `02` room1, `03` room2
- Integration이 보내는 패킷의 출발지는 **Master 주소 `0100`** 이다. 현재 버스에는 실제 월패드가 없으므로 Integration이 유일한 Master다.
- Boiler Controller가 Thermo 주소 `3600`~`3603`에 응답한다.

## Thermo 값 (8바이트)

| 바이트 | 의미 |
|---|---|
| 0 | `11` heat, `01` off |
| 1 | `01` 외출(Away), `00` 재실 |
| 2 | 설정 온도 (℃, 정수) |
| 3 | 미상 [검증 필요] |
| 4 | 현재 온도 (℃, 정수) |
| 5–7 | `00` |

- 모드가 off일 때 바이트 2의 의미는 불확실하다. 참조 구현은 off일 때 이 값을 무시했다. [검증 필요]

## 명령 (Integration → Thermo, cmd `00`)

| 동작 | 값 |
|---|---|
| 난방 켜기 + 설정 온도 T | `11 00 T 00 00 00 00 00` |
| 난방 끄기 | `01 00 T 00 00 00 00 00` (T = 마지막 설정 온도) |
| 상태 조회 | cmd `3a`, 값 전부 `00` |

- 설정 온도 변경 명령은 바이트 0이 `11`이므로 꺼져 있던 방을 켠다. 바이트 1이 `00`이므로 외출도 해제될 수 있다. [검증 필요]

## 송신 절차

1. **쓰기 타이밍**: 마지막 바이트 수신 후 최소 30ms가 지난 뒤 쓴다 (버스 충돌 회피). 연결 직후 아직 수신이 없으면 1초 대기.
2. seq `c`로 송신한다.
3. **ACK 대기** 1.3~1.5초(무작위). 기대 ACK: 타입 `30d`, 같은 seq, 목적지·출발지 뒤바뀜, 같은 명령·값.
4. ACK가 없으면 seq `d` → `e` → `f`로 재송신한다. 4번 모두 실패하면 명령 실패.
5. ACK 전에 상태 응답이 먼저 오면 ACK를 받은 것으로 간주한다.
6. **상태 응답 대기** 최대 2초: 타입 `ack`, 출발지 Wallpad, 목적지 = 대상 Thermo인 패킷의 값이 그 방의 최신 상태다.
7. 한 번에 하나의 송신만 진행한다 (직렬화).

## ⚠ Master 부재 시 상태 응답 [검증 필요 — 최우선]

참조 구현이 상태로 쓰던 패킷(타입 ack, 출발지 `0100`, 목적지 `36xx`)은 **실제 월패드가 Thermo의 상태 보고에 보낸 ACK**로 보인다. 즉 흐름은:

1. Master → Thermo: send (명령/query)
2. Thermo → Master: ack
3. Thermo → Master: send (상태 보고)
4. Master → Thermo: ack ← 참조 구현은 이 패킷의 값을 읽었다

현재 버스에는 실제 월패드가 없으므로 4번을 보낼 장비가 없다. 그렇다면:
- Integration은 **3번(Thermo → Master send)을 상태로 읽어야** 하고,
- Integration이 **4번 ACK를 직접 보내야** 할 수 있다 (보내지 않으면 Controller가 seq를 바꿔 재송신할 가능성).

캡처로 1~4번이 실제로 어떻게 오가는지 확인한 뒤 확정한다.

## 상태 갱신 (감청)

- 버스에서 **타입 ack, 출발지 Wallpad(`01xx`), 목적지 Thermo(`36xx`), 명령 `00`** 인 패킷이 보이면 해당 Room 상태로 반영한다. 참조 구현은 이 패킷만 상태로 사용했다.
- 참조 구현에 남은 주석으로 보아 Thermo → Wallpad 방향 send 패킷도 같은 값을 실을 가능성이 있다. [검증 필요]

## Polling

- Room마다 query(`3a`)를 1초 간격으로 순차 송신한다.
- 참조 구현은 Polling 주기 안에 감청으로 받은 패킷이 있으면 query를 생략했다 (캐시). 버스 점유를 줄이는 효과가 있으므로 동일하게 적용한다.
